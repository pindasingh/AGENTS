Checkout is accepted first.
Order processing continues asynchronously.

A compact review view of the authoritative Mermaid sequence in checkout-order-processing.mmd. This page does not render Mermaid and uses no external assets.

4 · Basket RedisRead customer basket
5 · Event busPublish UserCheckoutAcceptedIntegrationEvent
Exact acceptance boundary: only after publishing the checkout event, Basket returns HTTP 202 Accepted through the Web BFF to the browser. The browser does not wait for order creation or completion.

Shared asynchronous processing

  1. RabbitMQ (or the replaceable Azure Service Bus implementation) delivers UserCheckoutAcceptedIntegrationEvent to Ordering.
  2. Ordering dispatches idempotent IdentifiedCommand<CreateOrderCommand, bool> using RequestId.
  3. Ordering creates and commits the order in Ordering SQL, records integration events, then publishes OrderStartedIntegrationEvent and OrderStatusChangedToSubmittedIntegrationEvent.
  4. Basket consumes OrderStartedIntegrationEvent and deletes the checked-out basket from Redis.
  5. Ordering publishes OrderStatusChangedToAwaitingValidationIntegrationEvent; Catalog consumes it and checks Catalog SQL.

Stock confirmed → successful completion

  1. Catalog validates and decrements stock in Catalog SQL, then publishes the stock-confirmed result.
  2. Ordering consumes it, saves the changed state in Ordering SQL, and publishes OrderStatusChangedToStockConfirmedIntegrationEvent.
  3. Ordering SignalR Hub consumes that event and notifies connected clients; Payment also consumes it.
  4. Payment publishes OrderPaymentSuccededIntegrationEvent (spelling preserved).
  5. Ordering consumes it, marks the order paid in Ordering SQL, and publishes the paid status. Ordering SignalR Hub consumes order-status events and notifies connected clients.

Stock rejected → cancellation

  1. Catalog publishes the stock-rejected result.
  2. Ordering consumes it.
  3. Ordering cancels the order and saves it in Ordering SQL.

Evidence limits

The evidence requires a payment-failure variant but supplies no failure contract name, resulting state transition, store write, or notification. The authoritative diagram marks that gap rather than inventing behavior. It likewise does not supply exact contract names for stock-result events or the paid-status event.
