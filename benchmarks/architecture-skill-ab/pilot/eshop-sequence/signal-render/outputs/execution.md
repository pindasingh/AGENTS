# Benchmark execution

## Eval prompt

"Using only the supplied Microsoft eShopOnContainers evidence, create the most useful sequence diagram for an engineer who needs to understand checkout acceptance followed by asynchronous order processing. Show the web caller path, the exact point of the HTTP 202 response, successful completion, stock rejection, and every evidenced store, event, consumer, and notification involved. Preserve exact contract names where the evidence provides them, do not invent unsupported behavior, and make the final artifact self-contained and reviewable offline."

## Deliverables

- **Authoritative source:** `architecture/architecture.ts` (with the dependency-free DSL in `architecture/signal.ts`).
- **Data-only projection:** `architecture/architecture.json`; generated by `project-architecture.js`, which does not import or execute the TypeScript model.
- **Final offline artifact:** `architecture/index.html`.
- **Validation evidence:** `typecheck.log`, `renderer-compile.log`, `render.log`, `renderer-tests.log`, and `html-smoke.log`.

The model separates HTTP acceptance from asynchronous continuations. Its selectable paths cover accepted checkout, basket cleanup, successful paid completion, stock rejection, and an explicitly unresolved payment-failure variant.

## Uncertainties and evidence limits

- The fixture requires a payment-failure path but supplies no payment-failure event contract or resulting order state. The artifact terminates that path at the Payment consumer and labels the missing behavior; it does not invent an event or state transition.
- The fixture says Ordering publishes a paid status but does not provide that contract's exact name. The model uses the descriptive label `Order paid status integration event (contract name not supplied)` and marks the declaration unknown rather than asserting a likely class name.
- `OrderStatusChangedToStockRejectedIntegrationEvent` is inferred from the fixture's explicit stock-rejected publication/result and naming context; the curated evidence does not expose its source declaration.
- Azure Service Bus is documented only as an alternative implementation. The rendered runtime boundary is RabbitMQ, the evidenced development/test implementation.
- Browser interaction testing was not performed because the benchmark constrained execution to exactly the two supplied skills. Renderer tests and deterministic offline HTML smoke checks were run instead.
